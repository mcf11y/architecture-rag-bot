## 0. Постановка: кто ставит задачу и для кого мы её делаем

**Кто ставит задачу (спонсоры и лица, принимающие решения):**

- **CTO / VP Engineering** — отвечает за стек, стоимость владения, интеграцию с существующей инфраструктурой (AWS EKS, GitHub, Confluence).
- **CFO / руководство** — интересует прямой экономический эффект: сокращение FTE-затрат на поиск (инженеры теряют до 4 ч/нед) и снижение стоимости подготовки к аудитам (SOC 2 review ~140 ч GRC-команды).
- **GRC / Security / Compliance** — контролируют конфиденциальность данных, SOC 2, GDPR, поскольку компания европейская (Финляндия + Эстония, ЕС).

**Для кого мы делаем продукт (пользователи бота):**

- **Разработчики** — архитектурные решения (ADR), API-документация, описания микросервисов.
- **Служба поддержки** — типовые решения проблем пользователей (Zendesk, Google Docs).
- **Менеджеры и аналитики** — регламенты и бизнес-правила.
- **Новые сотрудники** — onboarding-инструкции.

**Вывод для архитектуры:** заказчик — не стартап, а зрелая продуктовая компания в ЕС с сертификацией SOC 2 и клиентами уровня ABB и Wärtsilä. Значит, ключевые нефункциональные требования — **безопасность, соответствие GDPR/SOC 2, предсказуемая стоимость и масштабируемость**, а не «сделать по-быстрому». Это напрямую влияет на выбор: часть данных нельзя бесконтрольно отправлять в публичное облако третьих стран.

## 2. Сравнение LLM-моделей: локальные (Hugging Face) vs облачные (OpenAI / YandexGPT)

Сравниваем по четырём критериям из задания: качество, скорость, стоимость владения и использования, удобство развёртывания.

- **Облачные (managed API):**
  - **OpenAI** — **GPT-5.5** (флагман, ~$5/$30 за 1М токенов вход/выход, силён в DevOps/terminal-задачах), бюджетные **GPT-5.4 mini/nano** (от ~$0.20/$1.25). Разворачиваем через **Azure OpenAI** в ЕС-регионе.
  - **Anthropic** — **Claude Opus 4.8** (лидер по агентному кодингу и сложному рассуждению, ~~$5/$25), повседневный **Claude Sonnet 5** (~~$3/$15), топовый **Claude Fable 5** (~$10/$50). Доступен в т.ч. через **AWS Bedrock** (ЕС-регион) — важно, т.к. инфраструктура заказчика уже на AWS.
  - **Google** — **Gemini 3.1 Pro** (чемпион по длинному контексту до 1–2М токенов и цене, ~$2–4/$12–18), быстрый дешёвый **Gemini 3.5 Flash / Flash-Lite** (от ~$0.25/$1.50).
  - **YandexGPT** — рассматриваем по требованию ТЗ.
- **Локальные (open-weight, Hugging Face), разворачиваем через vLLM/SGLang:**
  - **Qwen3.5 / Qwen3.6-35B-A3B** (Apache 2.0) — лучший общий open-weight выбор: мультиязычность (200+ языков), кодинг, MoE 35B/3B активных → влезает на одну GPU. Оптимум для нашего кейса.
  - **Mistral Small 4 / Mistral Large 3** (Apache 2.0) — европейский вендор, дружелюбны к EU data-residency, нативный function calling.
  - **Llama 4 Scout** — экстремально длинный контекст (до 10М токенов), но лицензия Meta Community и требовательность к железу.
  - **DeepSeek V4 / GLM-5.2 / gpt-oss** — сильные и дешёвые в инференсе альтернативы (MIT/Apache).

### 2.3 Ориентировочная экономика (порядок величин, для сравнения)

- **Облако (Azure OpenAI / AWS Bedrock, ЕС):** дешёвые тиры (Gemini Flash-Lite ~$0.25/$1.50, GPT-5.4 nano ~$0.20/$1.25 за 1М) — центы за типовой ответ; флагманы (GPT-5.5, Claude Opus 4.8 ~$5/$25–30 за 1М) — десятки центов за сложный ответ. Для внутреннего бота (сотни–тысячи запросов в день) это обычно **сотни–низкие тысячи $/мес**. Платим только за факт, старт почти бесплатный.
- **Локально (аренда GPU в облаке):** Qwen3.6-35B-A3B (MoE, INT4) влезает на одну GPU и это резко удешевляет self-host; но полноценный отказоустойчивый инференс = 1–2× **H100 80GB ≈ $2–4 тыс./мес** каждая (резерв) + зарплата MLOps. По индустриальной эвристике 2026 г. self-host окупается примерно **от ~1 млрд токенов/мес** или при жёстком комплаенс-требовании. Иначе облако дешевле.



### 2.4 Вывод по LLM

- **Оптимум для старта и для 80% корпуса:** облачный фронтир в ЕС-регионе через **Azure OpenAI** или **AWS Bedrock** (последний удобнее, т.к. инфраструктура уже на AWS). Маршрутизация по сложности: дешёвая быстрая модель (**Gemini 3.5 Flash / GPT-5.4 mini / Claude Sonnet 5**) для простых вопросов, флагман (**GPT-5.5 / Claude Opus 4.8**) для сложных. Лучшее качество, минимальный TCO, GDPR/SOC 2-совместимый DPA с гарантией неиспользования данных для обучения.
- **Для конфиденциального «ядра»** (ADR, Terraform, SCADA, спецификации заказчиков): **локальная open-weight модель** (**Qwen3.6-35B-A3B** как оптимум цена/качество, либо **Mistral Small 4/Large 3** — EU-вендор — через vLLM) в собственном контуре AWS ЕС — второй «приватный» маршрут.
- **YandexGPT — исключаем** по юрисдикции/комплаенсу.

Это подводит нас к **гибридной (роутинговой) архитектуре**: маршрутизация запроса на облачную или локальную модель в зависимости от грифа конфиденциальности источника.

## 3. Сравнение моделей эмбеддингов: Sentence-Transformers vs OpenAI Embeddings

Критерии из задания: скорость создания индекса, качество поиска, стоимость владения и использования.

### 3.1 Кандидаты

- **Локальные (Sentence-Transformers / HF):**
  - **BGE-M3** — мультиязычная, dense+sparse, до 8k контекста, топ по retrieval.
  - **multilingual-e5-large** — сильная мультиязычная, хорошо для EN/FI/ET.
  - **all-MiniLM-L6-v2** — быстрая и лёгкая (baseline, ниже качеством).
- **Облачные:**
  - **OpenAI text-embedding-3-large / -3-small** (через Azure OpenAI ЕС).



### 3.2 Сравнительная таблица


| Критерий                      | Sentence-Transformers (BGE-M3 / e5)                                                                        | OpenAI text-embedding-3                                                                                      |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Скорость создания индекса** | На GPU — очень быстро; на CPU — медленнее, но реально для батч-переиндексации. Нет сетевых лимитов         | Ограничена rate-limit API и сетью; батч-эмбеддинг 18k+ файлов упирается в квоты/латентность, но параллелится |
| **Качество поиска**           | BGE-M3/e5-large — топ на MTEB, отличная мультиязычность (важно для EN+FI+ET), гибрид dense+sparse у BGE-M3 | 3-large — очень высокое и стабильное качество, минимум настройки                                             |
| **Стоимость использования**   | Бесплатно по токенам; стоимость = железо для инференса (можно на CPU для батчей)                           | Плата за токены — дёшево (эмбеддинги на порядки дешевле генерации), но растёт с объёмом                      |
| **Стоимость владения (TCO)**  | Модель локальна → полный контроль, нет утечки контента при индексации; нужна поддержка пайплайна           | Минимум инфраструктуры; но весь корпус (в т.ч. конфиденциальный) уходит в API при индексации                 |
| **Приватность**               | Максимальная — контент не покидает периметр                                                                | Требует ЕС-региона + DPA; для секретного ядра всё равно рискованно                                           |
| **Vendor lock-in**            | Нет; можно сменить модель (нужна переиндексация)                                                           | Есть привязка к формату/размерности; смена = переиндексация                                                  |




### 3.3 Ключевое архитектурное соображение

При индексации через облачные эмбеддинги **весь корпус целиком** (включая конфиденциальные ADR/спецификации) отправляется провайдеру. Это более чувствительно, чем разовая отправка одного вопроса при генерации. Поэтому для конфиденциальных данных **локальные эмбеддинги предпочтительнее по умолчанию**.

Дополнительный плюс локальной модели: **инкрементальная переиндексация** ~400 стр./мес и полные пересборки не тарифицируются по токенам и не ограничены rate-limit.

### 3.4 Вывод по эмбеддингам

**Рекомендуем локальные эмбеддинги —** `BGE-M3` (или `multilingual-e5-large` как альтернатива):

- лучшая мультиязычность (EN + возможные FI/ET) и высокое качество retrieval;
- нулевая стоимость по токенам и полный контроль над приватным контентом;
- эмбеддинги дешёвы в инференсе — их можно считать даже на CPU для батч-задач, что снижает требования к GPU.

Единая модель эмбеддингов для всего корпуса (и облачного, и приватного маршрутов) упрощает архитектуру: одно векторное пространство, один индекс.

## 4. Сравнение векторных БД: ChromaDB vs FAISS

Критерии из задания: скорость поиска и индексации, сложность внедрения и поддержки, удобство работы, стоимость владения (с учётом инфраструктуры).

### 4.1 Природа инструментов

- **FAISS** (Facebook AI Similarity Search) — **библиотека** ANN-поиска, не полноценная БД. Хранит только векторы, не имеет встроенного хранилища метаданных, сервера, API, персистентности «из коробки» (только сериализация индекса в файл). Максимально быстрая, поддерживает GPU и продвинутые индексы (IVF, HNSW, PQ).
- **ChromaDB** — **векторная БД/движок**: хранит векторы + документы + метаданные, есть фильтрация по метаданным, персистентность, клиент-серверный режим, коллекции, CRUD, интеграция с LangChain. Под капотом для ANN использует HNSW (hnswlib).



### 4.2 Сравнительная таблица


| Критерий                    | FAISS                                                                                                     | ChromaDB                                                                                                             |
| --------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Скорость поиска**         | Наивысшая; тонкая настройка индексов (IVF/HNSW/PQ), опционально GPU. Оптимальна для очень больших наборов | Высокая на HNSW для сотен тысяч–миллионов векторов; для нашего объёма — более чем достаточно                         |
| **Скорость индексации**     | Очень быстрая, особенно с GPU и батчами                                                                   | Хорошая; удобная инкрементальная вставка (`add`/`upsert`)                                                            |
| **Метаданные и фильтрация** | Нет из коробки — метаданные хранишь отдельно (свой мэппинг id↔документ)                                   | Встроенное хранение метаданных и фильтры (`where`), что критично для RAG (фильтр по источнику/владельцу/версии/дате) |
| **Персистентность**         | Ручная сериализация индекса + отдельно метаданные                                                         | Встроенная (локальный persist или клиент-сервер)                                                                     |
| **Сложность внедрения**     | Выше: нужно самому строить слой хранения документов, метаданных, обновлений, удалений                     | Ниже: почти всё «из коробки», быстрый старт, отличная интеграция с LangChain                                         |
| **Поддержка/эксплуатация**  | Больше ручного кода → больше сопровождения                                                                | Меньше кастомного кода; есть серверный режим и Docker                                                                |
| **Обновление/удаление**     | Неудобно (пересборка/переиндексация частей)                                                               | Удобный upsert/delete по id — важно для устаревающего контента (2–3 мес)                                             |
| **Стоимость владения**      | Бесплатно (open-source), но «прячется» в стоимости разработки/поддержки обвязки                           | Бесплатно (open-source); ниже стоимость разработки за счёт готовой функциональности                                  |
| **Масштабирование**         | Отлично масштабируется по данным, но горизонтально — сам                                                  | Есть серверный режим; для очень большого масштаба — облачный Chroma или переход на managed (pgvector/Qdrant/Milvus)  |




### 4.3 Что важно именно для этого кейса

Требования RAG-бота QuantumForge:

1. **Фильтрация по метаданным** (источник: GitHub/Confluence/Zendesk; владелец; версия; дата) — нужна для персонализации ответов по ролям и для выявления устаревшего контента. → **ChromaDB даёт это из коробки, FAISS — нет.**
2. **Инкрементальные обновления** (прирост 400 стр./мес, устаревание через 2–3 мес) → нужны удобные upsert/delete. → **Преимущество ChromaDB.**
3. **Объём** (сотни тысяч чанков) — **не тот масштаб**, где FAISS-производительность становится решающим фактором. ChromaDB на HNSW справляется с запасом.
4. **Скорость вывода на рынок и простота поддержки** → **ChromaDB.**

FAISS выигрывает там, где корпус измеряется десятками–сотнями миллионов векторов и критична каждая миллисекунда/GPU-ускорение. Для внутреннего бота это избыточно и оборачивается лишней инженерной обвязкой.

### 4.4 Вывод по векторной БД

**Рекомендуем ChromaDB** как основную векторную БД для MVP и production внутреннего бота:

- встроенные метаданные + фильтрация (ключевое для RAG и для аналитики пробелов документации);
- удобные инкрементальные обновления/удаления под жизненный цикл контента;
- простое внедрение и низкая стоимость поддержки, отличная интеграция с LangChain;
- Docker/серверный режим для развёртывания в контуре AWS ЕС.

**FAISS** оставляем как:

- вариант для быстрого локального прототипа (минимальная зависимость);
- «запасной аэродром» на случай экстремального роста корпуса (или как ANN-движок внутри более крупной СУБД).

## 5. Рекомендуемая конфигурация сервера (CPU, RAM, GPU)

Требования к железу зависят от того, где крутится LLM. Разделим на компоненты.

### 5.1 Компоненты нагрузки

1. **Оркестрация RAG (LangChain, API-сервис, роутер)** — лёгкая CPU-нагрузка.
2. **Векторная БД (ChromaDB)** — CPU + RAM (HNSW держит граф в памяти).
3. **Эмбеддинги (BGE-M3)** — можно на CPU для батчей; GPU ускоряет индексацию.
4. **LLM-генерация** — либо облако (Azure OpenAI / AWS Bedrock, железо не нужно), либо локальная модель (нужен GPU).



### 5.2 Оценка памяти для ChromaDB/эмбеддингов

- Корпус ~18k MD + 3k стр. Confluence + 250 PDF → после чанкинга ориентировочно **сотни тысяч чанков** (грубо 300–800 тыс.).
- Вектор BGE-M3 = 1024 float32 ≈ 4 КБ. 500k векторов ≈ **~2 ГБ** только на векторы; с HNSW-графом и метаданными — заложим **8–16 ГБ RAM** с запасом.



### 5.3 Рекомендуемые конфигурации

**А. Если LLM — облако (Azure OpenAI / AWS Bedrock), локально только RAG + Chroma + эмбеддинги (рекомендуемый базовый сценарий):**

- **CPU:** 8–16 vCPU (напр. AWS `m6i.2xlarge`/`m6i.4xlarge`).
- **RAM:** 32–64 ГБ (Chroma-граф + эмбеддинг-модель + запас на рост).
- **GPU:** не требуется (эмбеддинги считаем на CPU батчами; при желании ускорить индексацию — временный GPU-инстанс на время пересборки).
- **Диск:** 100–200 ГБ SSD (индекс, кэш, документы).

**Б. Если добавляем локальную LLM для конфиденциального ядра (гибрид):**

- **GPU:** 1× **NVIDIA H100 80GB** (или 2× для HA/нагрузки) под **Qwen3.6-35B-A3B** (MoE, AWQ/INT4 — влезает даже на одну GPU) или Mistral Small 4/Large 3. Для плотных моделей 70B+ в fp16 нужно ~140 ГБ VRAM → либо квантизация, либо 2× 80GB.
  - Более экономно: **1× L40S 48GB / A10G** для моделей ~8–14B (baseline-качество), а Qwen3 30B-A3B в INT4 реально запускается и на **1× RTX 4090 24GB / L4**.
  - AWS-инстансы: `p5` (H100) / `p4d` (A100) или `g6e`/`g5` (L40S/A10G).
- **CPU/RAM:** 16 vCPU / 96–128 ГБ.



### 5.4 Вывод по инфраструктуре

Для старта достаточно **CPU-инстанса без GPU** (сценарий А) — самый дешёвый и быстрый путь к рабочему боту. GPU подключаем только когда/если понадобится приватная локальная LLM (сценарий Б).

## 6. Итоговые варианты конфигурации (3–4) и выбор лучшего

Сводим всё в целостные варианты «LLM + эмбеддинги + вектор-БД + инфраструктура».

### Вариант 1 — «Полностью облачный»

- **LLM:** облачный фронтир (GPT-5.5 / Claude Opus 4.8 + дешёвый тир Gemini Flash / GPT-5.4 mini). **Эмбеддинги:** облачные (OpenAI text-embedding-3 / Gemini). **Вектор-БД:** ChromaDB. **Железо:** маленький CPU-инстанс.
- **Плюсы:** быстрый запуск, минимальный TCO и MLOps, лучшее качество из коробки.
- **Минусы:** весь корпус (в т.ч. конфиденциальный) уходит провайдеру при индексации; максимальная зависимость от вендора; риски по SOC 2/NDA для секретного ядра.
- **Комплаенс:** приемлемо только с Azure OpenAI / AWS Bedrock в ЕС + DPA, и всё равно рискованно для самого чувствительного контента.



### Вариант 2 — «Полностью локальный / on-prem»

- **LLM:** Qwen3.6-35B-A3B / Mistral Large 3 / Llama 4 (vLLM). **Эмбеддинги:** BGE-M3 (локально). **Вектор-БД:** FAISS или ChromaDB. **Железо:** GPU-кластер (H100/A100).
- **Плюсы:** максимальная приватность, нет платы за токены, полный контроль.
- **Минусы:** высокий CAPEX/OPEX на GPU, нужна MLOps-команда, качество топовой генерации чуть ниже фронтира, дольше запуск.
- **Комплаенс:** идеально, но дорого и медленно на старте.



### Вариант 3 — «Гибрид с роутингом» ⭐ рекомендуемый

- **LLM:** роутер по грифу источника — облако (GPT-5.5 / Claude Opus 4.8 через Azure OpenAI / AWS Bedrock ЕС) для обычного контента, локальная open-weight модель (Qwen3.6-35B-A3B / Mistral) для конфиденциального ядра (ADR/Terraform/SCADA/спецификации).
- **Эмбеддинги:** **BGE-M3 локально** (единое пространство для всего корпуса).
- **Вектор-БД:** **ChromaDB** (метаданные с грифом конфиденциальности → маршрутизация).
- **Железо:** CPU-инстанс для RAG+Chroma на старте; GPU добавляем под локальную LLM во второй фазе.
- **Плюсы:** баланс качества, стоимости и приватности; конфиденциальные данные не покидают периметр; облако даёт топ-качество для основного объёма; масштабируемо и переиспользуемо (цель бизнеса).
- **Минусы:** сложнее архитектурно (роутер, две модели), поэтапное внедрение.



### Вариант 4 — «Экономный CPU-only MVP»

- **LLM:** облачный дешёвый тир (Gemini 3.5 Flash / GPT-5.4 mini / Claude Sonnet 5). **Эмбеддинги:** BGE-M3 на CPU. **Вектор-БД:** ChromaDB (локальный persist). **Железо:** один CPU-инстанс.
- **Плюсы:** минимальная стоимость, максимально быстрый запуск MVP, проверка гипотез.
- **Минусы:** нет приватного маршрута для секретов, качество ограничено дешёвым тиром модели.
- **Роль:** отличный **этап 0 / PoC**, эволюционирует в Вариант 3.

### Итого:

**Целевая архитектура — Вариант 3 (гибрид с роутингом)**, реализуемый поэтапно через **Вариант 4** как MVP:

1. **Фаза MVP (В4):** ChromaDB + BGE-M3 (CPU) + облачная модель дешёвого/среднего тира (Gemini 3.5 Flash / GPT-5.4 mini / Claude Sonnet 5 через Azure OpenAI / AWS Bedrock ЕС) на неконфиденциальном подмножестве корпуса. Быстро, дёшево, проверяем ценность.
2. **Фаза Production (В3):** добавляем гриф конфиденциальности в метаданные Chroma, роутер запросов и локальную open-weight LLM (GPU) для приватного ядра.

Это лучший баланс всех бизнес-целей: экономия FTE и быстрый запуск (облако), защита конфиденциальных данных и комплаенс (локальный маршрут), масштабируемость и переиспользование (единый индекс + метаданные + модульный роутер).
